🎛️ Orchestrator Harness Overview

How Purple Ruler's multi-agent engineering orchestrator actually runs (training edition, 2026-08-07). The orchestrator's job boundary: dispatch / gate / merge / report — it never writes product code itself. 13–14 resident dev agents do the coding across two production repos.

② The sweep — the only legal starting point for any "what's pending?" question

bash tools/orch-sweep.sh reads all five sources of truth in one command, paginating every query to has_more=false. Answering a status question from memory is forbidden.

  • Decision desk: pending / awaiting the owner / in-progress rows re-checked one by one (merged PR ⇒ close the row on the spot)
  • Publish board non-terminal rows + CE↔Velo liaison log awaiting relay
  • Open PR queue across both repos
  • Reply debt (merged but lane never told) + closure debt (row cites a PR that already merged)
  • Delivery ratio (feature delivery ≥30% of PRs is the bar) + lane context levels
  • The orchestrator's own P0 section — work nobody will ever chase you for

Iron rule: anything the sweep shows as done gets closed in the same command batch. An "in-progress" row must state what it is waiting for and on whom — if you can't write that sentence, it isn't in progress.

③ Acting — two single entry points

ActionCommandBuilt-in safety
Message a lanebash tools/cmux-say.sh <lane> '<text>'Live surface re-resolution (wrong-window proof) · three-step delivery protocol · post-send screen read as proof · logged
Merge a PRbash tools/pr-merge.sh <repo> <n>Stacked-PR detection (squash-orphan proof: MERGED ≠ landed on main) · always reply to the lane afterwards (a merge is not a receipt)

All agent-to-agent traffic is relayed through the orchestrator — frontend and backend lanes never message each other directly. Anything touching the shared low-code platform browser goes to the owner, never to an agent.

④ The gate pipeline — how a PR reaches production

lane opens PR→ CI (required checks)→ external second review
high-risk classes; quota-out ⇒ merge now, review later→ arm auto-merge
always read back mergeStateStatus→ verify landed on main
merge SHA = main tip→ receipt to lane→ batch → owner publishes
publish-board row exists before the publish, never after
  • Backend lanes: happy path merges autonomously. Frontend CE lanes: merge on green CI, verify live, revert if wrong.
  • Hard stops that go to a human: publishing anything on the money path; permission / payment / loop-class machine changes; bulk writes to production data need a spec gate first (sample reviewed, unknown values left blank, never invented).
  • Acceptance iron rule: "no errors" is not acceptance — you must be able to answer "if this silently broke, in which cell would I see a different value?"

"Stale-ledger bug" = dispatching or concluding from an old ledger entry after reality has moved on — the single most frequent failure class in multi-agent orchestration. The two iron rules in ② and ⑤ exist to kill it.
