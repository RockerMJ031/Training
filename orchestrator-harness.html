🎛️ 编排者 Harness 总览

Purple Ruler 多 agent 编排中心的运行机制(training 版,2026-08-07)。编排者的职责边界:派单 / gate / 合 PR / 汇报,不下场写代码;13-14 个常驻 dev agent 在两个真实代码仓上干活。

信号源机制要点

② 扫账 —— 每轮状态问题的唯一合法起点

bash tools/orch-sweep.sh 一条命令读全五处真源,全部翻页到 has_more=false,禁止凭记忆回答「有什么待办」:

  • 决策台:待处理 / 等负责人拍 / 处理中逐条过(PR 合了就当场销)
  • 发布台非终态 + CE↔Velo 联络日志待中转
  • 两仓 open PR 队列
  • 回执欠账(合并了没回 lane)+ 销账欠账(行里 PR 已合)
  • 交付比例(需求交付 ≥30% 达线)+ lane ctx 水位
  • 【编排者自己的 P0】段 —— 专治没人催的活滑走

铁律:扫出来的已完成项在同一批命令里立刻销账;「🔄处理中」必须写得出【在等什么、等谁】,否则它不该是处理中。

动作命令内建保险

④ Gate 流水线 —— 一个 PR 怎么走到生产

lane 开 PR→ CI(required checks)→ 外部二审
高风险类;额度尽则合后补审→ arm auto-merge
必回读 mergeStateStatus→ 落 main 核实
merge SHA = main tip→ 回执 lane→ 攒批 → 负责人 Publish
发布台先立行,禁事后补录
  • 后端 lane:happy path 自动合;前端 CE lane:CI 绿即合、线上验收、不对就 revert
  • 硬拦上桌:动钱链路的发布负责人亲跑;权限/支付/loop 类机器改动强制人审;批量写生产数据先过 spec 关(样例先审,未知值留空,绝不编造)
  • 验收铁律:「没报错」不是验收 —— 必须答得出「如果它悄悄坏了,我会在哪一格看到不一样的值」

⑤ 台账 —— 五张 Lark Base 表构成的共享记忆

表职责关键纪律
决策台三方信箱:agent 完工/卡点上报 · 负责人远程拍板 · 编排者派单销账写入带身份前缀;台账条目引用前先核现状(条目是写下那一刻的事实,不是现在的事实)
发布台每次发布的授权与批次记录行先于发布存在,禁止事后补录
联络日志跨 lane 消息中转记录「待发送」= 编排者当场转发
QE-Bug 台账缺陷全生命周期跟踪哨兵盯增量;条件触发单写清触发点与基线
Lane 状态板各 lane 心跳 + 日报锚点「最后更新」非自动字段,必须显式写

⑥ 断点续传 —— compact 不丢线

handover 文档
⚡一分钟接手表 + 重启后第一步清单→ 本地锚点文件
永远指向最新一份→ SessionStart hook
恢复后自动注入检查清单→ ps 核哨兵 + 扫账
TaskList 空 ≠ 哨兵死

实测:一次 compact 后 16 分钟内完成全部恢复动作(哨兵核活 / 欠投补投 / cron 重建 / 待合 PR 处置),零丢失。

⑦ 一天的量级(2026-08-07 实测样本)

37PR 合并(全天)
35%需求交付占比(线 30%)
14常驻 dev lane
5台账真源表
4台账过期病当日抓获

「台账过期病」= 引用台账旧结论派单/下结论,而现状早已变化 —— 这是多 agent 编排里最高频的错误族,对策就是 ②⑤ 里的两条铁律。
