00 · Why these three words · 2 min

Three pieces of paper, each written before something expensive

On Day 1 the chatbox evaporated (rung 1) and a good prompt fixed one conversation (rung 2). The three words today are what turns one person’s good prompt into something a second person — or the same person tomorrow — can pick up: the spec says what we are building and how we will know; the plan says in what order and touching which files; the handover doc says where we got to when the lights went out.

01 · Spec · 4 min

Spec · say it back in plain words before anyone builds

W1Spechouse rule: no approved spec, no code
Definition
Before writing any code, the builder writes back three things in plain language for the owner to confirm: ① what I understand you want; ② how I intend to do it; ③ acceptance criteria written as behaviour — “input X gives Y”, “click this, get that” — so someone who never reads code can verify it by using it. All unclear points are listed once, together; building starts only after the owner confirms [7]. The official guidance has the same shape for larger features: “have Claude interview you first … Keep interviewing until we’ve covered everything, then write a complete spec to SPEC.md.” Then: “Once the spec is complete, start a fresh session to execute it.” And: “The most useful specs are self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step that proves the feature works.” [1]
Analogy
A builder’s quote. You don’t discover the extension is on the wrong side of the house by inspecting the brickwork — you discover it on the drawing, where moving it costs a pencil line.
Counter-intuitive
The human check belongs at the front, not the end. Code review (a second model, a colleague, a gate) can answer “was this built correctly?”; it cannot answer “was this the right thing to build?” A misunderstood requirement, built perfectly, is the wrong thing done very well [7]. Corollary: an acceptance criterion that cannot be turned into one experiment is not a criterion but a wish — “the audit should be robust” fails; “If the audit insert fails, then the system shall still play the recording and the response shall carry auditDegraded: true” passes, because you can make the insert fail once and look at two things [8].
In a real project
Anthropic’s workflow: interview → SPEC.md → fresh session that only implements [1]. At Purple Ruler every work order passes a spec gate before a line is written: acceptance sentences must fit one of six EARS shapes (always / while / when / where / if-then / combined); unclear points go through a ten-class clarify list (scope, data model, user flow, non-functional, integrations, failure handling, trade-offs, terms, done-signal, scale) and anything unanswered is left in the document as a visible [NEEDS CLARIFICATION: …] marker — at most five questions per round, multiple choice preferred; an implementation may not start while a marker remains [8]. For guard-type work the spec is five fixed tables (decision points, truth table, break cells, mutation matrix, replace / not-do) and a script pre-checks them before a human reviewer sees it [9].
At the desk
The three-line template, in plain words: “Here is what I think you want: … Here is how I’ll do it: … You’ll know it works when: …” Your owner reads it in a minute and corrects it for free. That minute is the cheapest hour of the project.
02 · Plan · 3 min

Plan · the order and the files, approved before the first edit

W2Plan · plan modeShift+Tab · /plan · claude --permission-mode plan · Ctrl+G
Definition
A plan is the steps, the files each step touches, and the order — proposed by the builder, approved by the owner before anything is executed; the builder proposes the order so the owner never has to dictate it step by step [7]. Claude Code has a mode for exactly this: “Plan mode tells Claude to research and propose changes without making them. Claude reads files, runs shell commands to explore, and writes a plan, but does not edit your source … edits stay blocked until you approve the plan.” Enter with Shift+Tab (status bar shows ⏸ plan mode on), prefix one prompt with /plan, or start with claude --permission-mode plan. “When the plan is ready, Claude presents it and asks how to proceed”: approve and run in auto mode, approve and review each edit, or “No, keep planning”; Ctrl+G opens the plan in your editor to change it directly [4][5].
Analogy
The route on the map, agreed with the passenger before the engine starts. The spec said where and how you’ll know you arrived; the plan says which roads, in which order.
Counter-intuitive
Planning has a price, and the docs say so: “Plan mode is useful, but also adds overhead … If you could describe the diff in one sentence, skip the plan.” [1] Plan when you are unsure of the approach, the change touches several files, or the code is unfamiliar [1]. And a plan is one of the few things that survives compaction — it is re-injected from disk along with CLAUDE.md [3] — so a plan on paper is also insurance.
In a real project
Anthropic’s recommended four phases: Explore (plan mode, read, ask) → Plan (“what files need to change? create a plan”, edit it with Ctrl+G) → Implement (approve, then “implement from your plan, write tests, run them”) → Commit [1]. At Purple Ruler the plan gate follows the spec gate: a work order lists its steps and files, the owner approves, then tests are written to fail first and the implementation turns them green [7].
At the desk
For a non-code task the plan is the same three columns — step · what it touches · order — in a message the owner can tick. “1 draft the letter (file A) · 2 you check the two facts · 3 I send to the group”: thirty seconds to write, and it stops step 3 happening before step 2.
03 · Handover doc · 4 min

Handover doc · the only thing that crosses the gap

W3Handover docwritten before compact · read first after
Definition
A file, written by the person or lane doing the work, before memory is lost, that the next session reads first. It holds five kinds of fact: coordinates (where things live), in flight (what is half-done and on which branch or ticket), waiting on whom, needs the owner (decisions only a human can make), and precedents (what we learned the hard way this segment). Why a file and not the chat: “Each new session starts with a fresh context window, without the conversation history from previous sessions” [2]; compaction “keeps your requests and key code snippets, but detailed instructions from early in the conversation may be lost” [2]; and only the root instruction file, auto memory and the plan come back from disk by themselves [3].
Analogy
The ward handover at shift change. The night nurse does not hope the day nurse “remembers”; she writes the sheet — who is on what, what changed, what is due, who to call — and the day nurse reads it before touching a patient.
Counter-intuitive
① Write it before the loss, not after. The summary that compaction produces is written by the model from what is left; you cannot audit which half went missing (Day 1, Figure 2). The hand-written file is written by you, from the full picture, while you still have it. ② A handover must carry its own probes: one to three commands with the expected output (“this PR should still be OPEN”, “this file should exist”). The next session runs them first; if any fails the note is stale and it stops instead of acting on an old picture. A note without probes reads just as confidently when it is wrong. ③ It is append-only and dated — you never edit history, you add a section, so the trail of what was believed when stays readable.
In a real project
Our coordinator keeps one progress file in git, one dated section per compaction, each section opening with a fixed “ten lines to recover”: ① coordinates unchanged · ② waiters that die on restart and must be re-armed · ③ merged this segment · ④–⑦ one line per live workstream · ⑧ everything else in flight · ⑨ what needs the owner · ⑩ new precedents, numbered [10]. A private, git-ignored pointer file on each machine says only where that anchor lives — because anything you rely on to recover from a disaster cannot live in the place the disaster destroys [10]. Day 1’s case B is this habit under pressure: “write to the board and the handover file, reply ‘saved’, then compact”. The official advice for the model’s own summary is the same instinct, one size smaller: tell CLAUDE.md “When compacting, always preserve the full list of modified files and any test commands.” [1]
At the desk
Five lines at the end of your working day, in a file you’ll open tomorrow: where I am · what is half-done · who I’m waiting on · what I need from my manager · one thing I learned. Write it while you still know; tomorrow’s you reads it before opening anything else.
INSIGHT D2·1

Spec before code, plan before edits, handover before forgetting. Each is a page written while changing your mind is still free. Review at the end checks the work. Only paper at the front checks the intent.

04 · Hands-on · 2 min

Write the handover for what you are doing right now

Open a text file. Five lines: where I am · what is half-done · who I’m waiting on · what I need from my manager · one thing I learned today. Zero names, zero credentials.
Add one probe: a fact a colleague could check in ten seconds that would tell them the note is out of date (“the draft is still in the shared folder”, “the ticket is still open”).
Paste it to the group. Tomorrow, read someone else’s and say whether you could start from it cold.
05 · Term cards

Today’s three words, one line each

Spec
Plain-words write-back before any build: what I understand · how I’ll do it · how you’ll know it works (behaviour sentences). Unclear points listed once; nothing built until confirmed.
Plan · plan mode
Steps, files, order — approved before the first edit. In Claude Code: Shift+Tab; reads and proposes, edits nothing until you say yes. Skip it for one-sentence diffs.
Handover doc
A dated, append-only file written before memory is lost: coordinates · in flight · waiting on whom · needs the owner · precedents, plus probes. Read first, next session.
