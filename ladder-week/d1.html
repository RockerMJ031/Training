00 · Why this week · 2 min

Five days, one ladder, one hour a day

Everyone here already uses AI. The Ladder showed six rungs and argued that the gap between a quick answer and a working system is which rung you hold the tool from. This week we climb it one rung a day, together, in Claude Code, on our own work.

01 · Rung 1 recap · 2 min

Rung 1 · The chatbox: everything evaporates

✋ SOUND FAMILIAR?
  • You explained the same thing to the AI on Monday, on Wednesday, and again on Friday?
  • A great answer last week — and you can’t find it, so you start over?

Rung 1 is where everyone starts: open a chat, type, get an answer, close the tab. The answers are fine; the problem is that nothing survives. The docs say it plainly: “Each new session starts with a fresh context window, without the conversation history from previous sessions.” [17] The whole week is about moving things out of the chat and into something that lasts — a reusable prompt today, a file tomorrow, rules the tool cannot break on Day 3.

02 · Nine term cards · 18 min

Nine words you need before you type

Each card has the same five rows: definition (the official sentence), analogy, counter-intuitive (the thing people get wrong), in a real project (Anthropic’s own teams), and at Purple Ruler (what it corresponds to in our repos — zero names, zero credentials).

T1Context window/context · ctx % on the status bar
Definition
“Claude’s context window holds your conversation history, file contents, command outputs, CLAUDE.md, auto memory, loaded skills, and system instructions.” [17] Before you type anything, CLAUDE.md, auto memory, MCP tool names and skill descriptions are already in it [16]. Numbers: auto memory loads only its first 200 lines or 25 KB [17]; after compaction the five most recently touched files are re-read, over 5,000 tokens as a path only [16]; current models compact automatically near their limit instead of ending your session [16].
Analogy
A whiteboard in a meeting room. Useful while there is space. When it is full you photograph it and wipe it (compact — you keep a picture), or you walk into a fresh room (clear — nothing comes except what you wrote on paper).
Counter-intuitive
A big window is not permission to ignore it: “LLM performance degrades as context fills” [1]; Anthropic’s engineers call it an “attention budget” and note that as context grows “the model’s ability to accurately recall information from that context decreases” [14]. And the summary “keeps your requests and key code snippets, but detailed instructions from early in the conversation may be lost” [17] — so rules you need to keep go in CLAUDE.md, not in the chat. One enormous file or tool output can make compaction spin; Claude Code stops with a thrashing error rather than loop forever [17].
In a real project
Run /context to see who is using the space. Anthropic’s own pattern is to hand investigation to a subagent that reads in its own window and returns a summary, keep MCP tool definitions deferred, and load skills on demand [17][16].
At Purple Ruler
The hand-over file every lane writes before it compacts (case B), and the rule “ctx past 50 % → write state to disk first”.
When to compact
Official current advice [16][1]: it compacts automatically near the limit. Better: compact earlier, with a focus — /compact focus on the auth bug fix before starting a long new task, so the summary keeps what you chose; /rewind to summarise only part of the conversation; /autocompact 500k to move the threshold. Between unrelated tasks don’t compact, /clear: “Old conversation crowds out the files you need next and costs tokens on every message.” [16] After two failed corrections it is not compact either — it is /clear plus a better first prompt [1]. And tell CLAUDE.md what compaction must keep: “When compacting, always preserve the full list of modified files and any test commands.” [1]
T2Model/model · status-bar field 4
Definition
Which brain is answering. The official aliases: sonnet “for daily coding tasks”; opus “for complex reasoning tasks”; haiku “the fast and efficient Haiku model for simple tasks”; fable “for your hardest and longest-running tasks”, “suited to tasks larger than a single sitting” — root-cause investigations, outage debugging, architecture decisions; opusplan plans on Opus, executes on Sonnet [4]. The list changes; the picker is the truth, not this card.
Analogy
A firm’s staff list. Different people cost different amounts per hour and are good at different things — and the list on the wall today is the only one that counts.
Counter-intuitive
① Bigger is not better: “Sonnet handles most coding tasks well and costs less than Opus. Reserve Opus for complex architectural decisions or multi-step reasoning.” [3] Across enterprises the average is about $13 per developer per active day, 90 % under $30 — and “unexpectedly high spend … usually traces back to long sessions that were never cleared or to Opus left as the default model” [3]. ② Switch to Opus and your subagents follow — research and test runs then cost Opus prices too [4]. ③ A weekly limit is shared by all models, so switching does nothing; an Opus limit can be worked around by switching family [3].
In a real project
Anthropic’s guidance for parallel work: “Use Sonnet for teammates”, and model: haiku in a subagent definition for simple delegated tasks [3]. Their growth-marketing team runs two specialised sub-agents over ad CSVs — “hundreds of new ads in minutes instead of hours” [15].
At Purple Ruler
Fourteen lanes, each with its own model shown on the status bar; the orchestrator plans on the strong model and dispatches routine lanes on the cheaper one — same shape as opusplan.
T3Effort/effort · inside /model
Definition
How much work it puts into the whole answer — “The effort parameter affects all tokens in the response”: thinking, the text, and the tool calls. Low effort tends to “combine multiple operations into fewer tool calls … proceed directly to action without preamble”; high effort tends to “make more tool calls … explain the plan before taking action”. “Effort is a behavioral signal, not a strict token budget.” [11] The Claude Code table reads like a supervision scale: low “Quick exchanges where you review each result”; medium “day-to-day engineering work with a clear scope”; high “Work where verification matters or edge cases are likely”; xhigh “Deeper reasoning at higher token spend”; max “Hard problems you want Claude to work through without you … test before adopting it broadly” [4]. Defaults: medium on Opus 5.5 / Sonnet 5.5 / Haiku 5.5, high elsewhere [4].
Analogy
Briefing a new colleague. Standing next to them, correcting any slip at once — you want a quick answer now. Walking into a two-hour meeting without looking back — you want them to think it through before touching anything. The right amount of thinking follows how far you step away, not how important the task feels.
Counter-intuitive
① max “adds significant cost for relatively small quality gains, and on some structured-output or less intelligence-sensitive tasks it can lead to overthinking” [11]. ② Low is not dumb: on Fable 5 “lower effort settings … often exceed xhigh performance on prior models” [11]. ③ On Opus 5 “changing effort does not reliably shorten responses” — ask for length directly [11]. ④ The longer you step away the less you can use low: Haiku 5.5 at low is “more likely to skip a search, stop early, or skip a check” in long agent tasks [11]. ⑤ Saying “think less” in the prompt is unreliable on Sonnet 5.5 / Haiku 5.5 — turn the dial [10]. ⑥ Research-grade: on four task families more reasoning lowered accuracy — counting with distractors, regression with misleading features, deduction with many constraints, risk assessment; Claude models “become increasingly distracted by irrelevant information” [13]. The Opus 4.6 release recommended “dialing effort down from its default setting (high) to medium” where it over-thinks [12].
In a real project
/effort or the arrows inside /model; a skill or subagent can carry its own effort in frontmatter; /usage literally suggests “Switch from max to high effort” when that is where your tokens go [3][11].
At Purple Ruler
Lanes run routine registration at medium and architecture rulings at high; case D shows the same small edit on two settings.
T4Token & usage/usage · status-bar fields 6–7
Definition
A token is the unit everything is counted in — roughly three-quarters of an English word. “Claude Code sends your full conversation with every request”, so “a one-line question in a session that has been open all day still draws usage for the whole conversation” [3]. A cache makes re-reading the same prefix cheaper; come back after the cache lifetime and the first message re-processes everything [3]. Numbers: average about $13 per developer per active day, $150–250 a month; background functions under $0.04 a session; /usage shows 24 h / 7 d and recommends changes for anything over 10 % of your usage [3].
Analogy
Mobile-plan minutes with a daily cap and a weekly cap — except a long conversation is a conference call that redials everyone each time you speak.
Counter-intuitive
① “/compact reads the conversation it summarizes, so compacting a large context is itself a large request. When you want a fresh start instead of continuity, /clear costs nothing.” [3] ② It spends while idle: scheduled loops, cross-session messages and goal check-ins each resend the whole context [3]. ③ Thinking is billed as output, and “the billed output token count does not match the visible token count” — you see a summary, you pay for the full reasoning [10]. ④ One debugging session can cost more than a day of chat [3].
In a real project
/usage attribution shows what skills, subagents and MCP servers cost; a hook can grep a log before Claude sees it — tens of thousands of tokens down to hundreds [3]; keep CLAUDE.md under 200 lines, move occasional instructions to skills [3]. Anthropic’s inference team cut research from an hour to 10–20 minutes by asking instead of reading — an “80% reduction in research time” [15]: spend tokens where they replace your time.
At Purple Ruler
The two daily glances the Ladder page recommends: ctx, and the usage windows [9]. Lanes /clear between unrelated tickets; the orchestrator’s skill list is the single biggest standing cost (T9).
T5Promptwhat you say this time
Definition
“Claude responds well to clear, explicit instructions.” “Providing context or motivation behind your instructions … can give Claude more information about your goals.” Examples are “one of the most reliable ways to steer Claude’s output format, tone, and structure”; tags separate instructions from input; one sentence of role is enough [19].
Analogy
A request to a colleague — one you will not be in the room to clarify.
Counter-intuitive
① Current models are “trained for precise instruction following”: “If you say ‘can you suggest some changes,’ Claude will sometimes provide suggestions rather than implementing them” [19]. ② Old-style shouting backfires — the official fixes are “Remove over-prompting”, “soften any aggressive language”, and “Use effort as a fallback” [19]. ③ “Tell Claude what to do instead of what not to do.” [19] ④ Write “Avoid over-engineering. Only make changes that are directly requested” or it will tidy things you didn’t mention [19]. ⑤ Opus 4.6 has “a strong tendency to use subagents” even for a simple search [19]. ⑥ The middle of a long prompt is recalled worst (Figure 9). ⑦ “Vague prompts can be useful when you’re exploring” [1].
In a real project
The four before/after pairs in §06 are the docs’ own [1]; for big features, “have Claude interview you” and write SPEC.md, then execute in a fresh session [1]; Anthropic’s security team: pseudocode first, then test-driven, “checking in periodically” [15].
At Purple Ruler
Every lane’s dispatch note starts with role, background and the don’ts; case A is the shape.
T6Instruction fileCLAUDE.md · rules · auto memory · /init · /memory · /doctor
Definition
CLAUDE.md is “instructions you write”; auto memory is “notes Claude writes itself based on your corrections and preferences”. Both: “Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead.” [2] Layers: organisation policy → ~/.claude/CLAUDE.md (you, all projects) → ./CLAUDE.md (team, in git) → ./CLAUDE.local.md (you, ignored by git) → subdirectory CLAUDE.md (loaded on demand) → .claude/rules/*.md (can be scoped to paths); all “concatenated … rather than overriding” [2].
Analogy
The staff handbook versus a request. You don’t re-explain the dress code in every email.
Counter-intuitive
① “Bloated CLAUDE.md files cause Claude to ignore your actual instructions!”; aim under 200 lines; “If you emphasize many lines, none of them stands out.” [1] ② Two rules that conflict: it “may pick one arbitrarily” [2]. ③ Nested CLAUDE.md and path-scoped rules are summarised away at compaction — must-survive rules go in the project root [16]. ④ It is not a lock (T9, §03).
In a real project
Three things about CLAUDE.md in project work: it loads every session and comes back from disk after compact [16]; it holds only what the model can’t guess — commands, style that differs from defaults, how to run tests, repo etiquette, gotchas — not tutorials, not things that change often [1]; it is maintained like code: read it when something goes wrong, prune it, change a line and watch whether behaviour moves; /doctor proposes cuts [1]. New data scientists at Anthropic have Claude “read the codebase’s CLAUDE.md files” first [15]; Boris Cherny’s team keeps one in git and adds a line whenever Claude gets something wrong [7].
At Purple Ruler
Each repo has one — our staff handbook for the tool. One real line: “never put a key, a secret or private data into a static asset”. Zero credentials, zero names, lives in git; a .claude/rules/ folder holds the file-type-specific ones.
T7Compact / clear/compact · /clear · /rewind · /btw
Definition
/compact replaces the conversation with a structured summary; /clear starts a fresh one with empty context; /rewind can summarise only a stretch; /btw asks a side question that never enters history [1][16].
Analogy
Photograph-and-wipe versus a new room (Figure 2).
Counter-intuitive
Compact is not free and not neutral: it is a large request [3] and a model-written summary [17]. Clear is free and loses nothing you wrote to disk. After two failed corrections the right move is clear, not compact [1].
In a real project
See “When to compact” under T1: early, with a focus, before a long task; clear between unrelated tasks; a Compact Instructions section in CLAUDE.md [16][17].
At Purple Ruler
Case B: write the hand-over file, reply “saved”, then the sentinel compacts — never the other order.
T8Permission mode & plan modeShift+Tab · /permissions
Definition
The step-away dial. Official “best for” text: Manual “Reviewing every action yourself, sensitive work”; acceptEdits “Iterating on code you’re reviewing”; plan “Exploring a codebase before changing it” (Claude reads and proposes, edits nothing until you approve); auto “Long tasks, reducing prompt fatigue” — a classifier blocks the risky actions (downloading and executing code like curl | bash, sending sensitive data to external endpoints, production deploys and migrations, mass deletion on cloud storage, force push); dontAsk for locked-down CI; bypassPermissions “Isolated containers and VMs only” [18].
Analogy
How far you walk from the new colleague’s desk. This is the x-axis of Figure 5: Manual ↔ low effort, acceptEdits ↔ medium, auto on a long task ↔ high / xhigh.
Counter-intuitive
“Auto mode reduces permission prompts but does not guarantee safety. Use it for tasks where you trust the general direction, not as a replacement for review on sensitive operations.” [18] And plan mode has a cost of its own: “If you could describe the diff in one sentence, skip the plan.” [1]
In a real project
Pre-approve the commands you trust with /permissions, cycle modes with Shift+Tab, start a big change in plan mode and approve the plan before anything touches disk [1][18].
At Purple Ruler
Lanes run in auto mode behind hooks (§03) — the dial is turned up because the locks are there, not instead of them.
T9Hook · skill · subagentthree extensions, three jobs
Definition
Hook — a lock: “Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens” [1] (§03). Skill — a folder of instructions loaded on demand: descriptions are always in context, the body only when invoked [20] (§04). Subagent — a helper with its own context window that returns a summary; by default it inherits your session’s model, so set model: haiku for simple jobs [4][17].
Analogy
A lock on the door · a binder you open when needed · an assistant you send to the archive so the files never land on your desk.
Counter-intuitive
Subagents’ requests still count against your usage [3]; agent teams run at roughly 7× the tokens of a single session [3]; the orchestrator can over-use subagents for things a simple search would do [19].
In a real project
Anthropic’s advice: “Use subagents for investigation” so the main window stays clean [1]; skills for workflows you invoke by name; hooks for “actions that must happen every time with zero exceptions” [1].
At Purple Ruler
bash-guard (a hook, §03), the lark-* skills (§04), and the orchestrator dispatching fourteen lanes — each lane is, in effect, a subagent with a status-bar line of its own.
INSIGHT D1·1

Context fills, models differ, effort follows how far you step away, tokens are the bill, files are the only thing that lasts — and only a hook is a lock. Nine words. If a session surprises you, one of them is the reason.

03 · What a hook physically does · 4 min

A hook is a lock — the model never gets a vote

Day 3 goes deep on this; today you only need the mechanism, because it explains why “I told it not to” keeps failing and why one of our pitfalls (the email that got sent) has a permanent fix.

Definition. Hooks are “user-defined shell commands, HTTP endpoints, MCP tool calls, LLM prompts, or subagents that execute automatically at specific points in Claude Code’s lifecycle” [21]. The point we care about is PreToolUse: “Before a tool call executes. Can block it.” [21] Compare the instruction file: “Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead.” [2]

Physically, in three steps

Claude decides to call a tool — say Bash with rm -rf /tmp/build, or the mailbox tool’s send.
Before running it, Claude Code serialises the call to JSON and writes it to your script’s stdin: {"tool_name":"Bash","tool_input":{"command":"rm -rf /tmp/build"}}.
Claude Code reads your script’s exit code. “Success: your hook exits 0” ⇒ the tool runs. “Blocking error: your hook exits 2” ⇒ “Claude Code stops the action”, and “the message that comes with the block is your hook’s stderr” — that sentence is handed back to the model, which then changes approach. Any other exit code is a non-blocking error: the action proceeds. And “Claude never sees stderr from a hook that exits 0.” [21] Finer control: exit 0 and print JSON with permissionDecision = allow / deny / ask / defer [21].

The official example, verbatim shape

In settings.json, a PreToolUse hook on Bash runs a small script; the script reads the command with jq and denies anything containing rm -rf [21]:

#!/bin/bash  — block-rm.sh (official walkthrough, path changed)
command=$(jq -r '.tool_input.command')
if echo "$command" | grep -q 'rm -rf'; then
  echo '{"hookSpecificOutput":{"hookEventName":"PreToolUse",
         "permissionDecision":"deny",
         "permissionDecisionReason":"rm -rf is blocked"}}'
fi
exit 0

Official step 5: “When the script denies a call, Claude Code reads the JSON decision, blocks the tool call, and shows Claude the reason.” [21]

Two real locks at Purple Ruler (zero names, zero credentials)

A
The “send” lock — pitfall 3, solved for good
The coordinator’s global settings.json carries one PreToolUse hook whose matcher is the four sending tools of the shared-mailbox integration: reply, reply-all, forward, send. However the prompt is phrased — “send it”, “fire it off”, “just reply” — the call is stopped before it happens; Claude can only draft. This is the physical object behind Day 3’s sentence “make it a rule the tool cannot break”.Case C below shows the same email with and without this lock.
B
bash-guard — every shell command goes through it
A 247-line script in the repo’s tools/hooks/. Rules live in a separate file — id · regex · the fix to use instead · exemptions · scope — e.g. block rm -rf, block git reset --hard inside a code repo. Structure follows the official example: allow(){ exit 0; }; a denial prints one line to stderr — [bash-guard] denied: <rule id> ⇒ use <fix> — then exit 2. Two things worth saying aloud: ① if the guard itself is broken it also denies (jq missing, rules file gone, stdin not JSON ⇒ still exit 2, with a different sentence so the reader can tell “you broke a rule” from “the lock is broken”) — fail-closed; ② it has --selfcheck, run at the start of every gate pre-check, so a lock cannot silently stop working. Measured: an rm -rf probe is denied with rc=2; ls passes with rc=0.Why the stderr sentence names the fix: the model reads it and takes that route — the lock also teaches.
INSIGHT D1·2

A sentence in a file is read by the model. A hook is run by the program. Only the second one is a lock. If something must never happen, don’t write it bigger — move it to lane 2.

04 · Skills: auto or by hand? · 3 min

Which skills should fire on a keyword — and which must not

Mechanism. “Skill descriptions are loaded into context so Claude knows what’s available, but full skill content only loads when invoked”; “the description helps Claude decide when to load the skill automatically.” [20] “Keyword-driven” therefore means: the model compares what you typed with every skill’s description / when_to_use (“trigger phrases or example requests”), and on a match the whole SKILL.md enters your context [20].

SwitchEffectOfficial use
disable-model-invocation: true“Claude can’t invoke the skill on its own” — only you, by typing /name. If Claude tries to work around it, “Claude Code blocks the call and instructs it not to reproduce the deploy steps another way.”“workflows with side effects or that you want to control timing, like /commit, /deploy, or /send-slack-message”; “You don’t want Claude deciding to deploy because your code looks ready.” [20]
user-invocable: falseHidden from the / menu; the model fetches it when relevant.“background knowledge that isn’t actionable as a command” [20]
skillOverrides in settingsuser-invocable-only (model can’t see it, you can type it) · off (hidden from both) — without editing someone else’s SKILL.md; the /skills menu can write it for you.Taming a plugin’s skill that fires too often [20]

Four rules for “not on a keyword”

1
It has side effects
Sends a message or email, deploys, writes a ledger, changes production data ⇒ disable-model-invocation: true, you type it. Same logic as the hook: “looks like it should be sent” is not “should be sent”.
2
Timing matters
Runs once a day, or waits for a human decision (a daily report, a group broadcast) ⇒ manual.
3
The description is too wide
If it is all common verbs (“analyse”, “tidy”, “report”) it will match one message in three ⇒ narrow the description (write when NOT to use into it) or make it manual.
4
It is a large reference document
One accidental trigger loads all of it, and “its content stays in context across turns … every line is a recurring token cost” [20] ⇒ split it, or user-invocable: false so only the model fetches it when truly needed.

At Purple Ruler. The lark-* family — read a doc, read a table, look up a contact — is right to auto-trigger on its description: read-only, no side effects. “Post to the group”, “write the ledger”, “build the daily report and DM it” (one of ours writes a Lark table and sends private messages) should be disable-model-invocation: true and typed by a person. The coordinator’s own rule is the same shape: anything sent in MJ’s name goes only on an explicit instruction, draft seen first.

05 · Pitfalls & fixes · 4 min

Twelve ways a session goes wrong — six to know by heart

Every pitfall is symptom → which of the nine words → fix. Don’t read all twelve; find the one that happened to you this week.

The long session gets slow and strange, then starts forgetting
WORDT1 / T7. Context is nearly full and recall falls as it fills [14]; compaction summarised away the detail you relied on [17].
FIXHave it write progress to a file, then /clear and start from that file. Two failed corrections on the same point ⇒ same answer: “Run /clear and start fresh with a more specific prompt” [1] (Figure 18).
You asked it to change one thing; it changed five
WORDT3 / T8. Effort too high for a one-line job — at lower effort it “scopes its work to what was asked rather than doing more than requested” [11] — and the permission mode let edits through.
FIXSay the boundary out loud (“only X, nothing else”), turn effort down for small changes [12], and for anything bigger than a sentence start in plan mode and approve the plan first [1][18].
You asked it to “send” the email — and it sent it
WORDT9. The verb was send, a sending tool was connected, and no hook stood in the way.
FIXToday: “draft only, do not send”. Permanently: the lock in §03 example A — a line in a file is advice, a hook is a lock [1][2].
It said “Done!” — and it wasn’t
WORDT5 (the ask had no check in it). “Claude stops when the work looks done.” [1]
FIXAsk for evidence, not a claim: the command output, the screenshot, the read-back. “Have Claude show evidence rather than asserting success.” [1] House version: “no error” is not “verified”.
You pasted something sensitive (a pupil’s name, a password)
WORDT1 / T6. Everything in the context can end up in transcripts, memory files and logs [2][17].
FIXNever paste it. Placeholders: “the pupil”, “the school”. This whole week runs with a zero-names, zero-credentials rule — practise it in the hands-on.
Same question, two different answers
WORDT5. No example and no fixed format, so it guessed twice; the model is not deterministic.
FIXGive one example of a good result and name the format. Facts that never change go into CLAUDE.md, not into the prompt (case E).
Six more we see every week · 07–12
You complained about the format but never showed one
WORDT5. It can only guess what “nicer” means.
FIXOne example beats three adjectives — a small, typical set, not every edge case [19]. Paste a result you liked and say “like this”.
You used the wrong model and paid for it
WORDT2 / T4. Opus left as the default for a bulk, routine job — or Haiku asked for a judgment call.
FIXLook at status-bar field 4 before you start. Surprise spend “usually traces back to long sessions that were never cleared or to Opus left as the default model” [3].
You assumed it remembered yesterday
WORDT1. “Each new session starts with a fresh context window” [17]; nothing crosses unless it was written to a file.
FIX/resume to pick up the old session [5], or — better — write the conclusion into a file and start clean.
One message, five jobs; it did two well and lost three
WORDT5. The official name is the kitchen-sink session [1].
FIXOne job per ask, /clear between unrelated ones [1][16]. Or ask for the plan first and tick the parts off.
It read two hundred files and the window was gone before it started
WORDT1 / T9. “The infinite exploration” [1] — investigation in the main window.
FIX“Use subagents for investigation” [1]: the reading happens in another window; only the summary comes back.
The draft came back wrong, so you blamed the AI
WORDT5. “Claude can infer intent, but it can’t read your mind.” [1]
FIXRe-read your own ask against the five elements of rung 2 (§06): role, background, example, format, don’ts. Which one was missing?
06 · Rung 2 · Asking well · 5 min

Rung 2 · The prompt: asking well, by hand

✋ SOUND FAMILIAR?
  • Do your best prompts live in a notes file you paste from — and drift a little every time?
  • Does a colleague doing the same job get different quality from the same tool? Why would that be?

Rung 2 is the discovery that how you ask changes everything. A good ask has five parts. You won’t need all five every time — but when a result disappoints, one of them is missing.

ElementWhat it isOne line you might write
RoleWho it is being, for whom“You draft replies for our school-support team.”
BackgroundThe three facts that change the answer“The school is asking about a start date we have not confirmed yet.”
ExampleOne good result to copy the shape of“Here is a reply we sent last term that was about right: …”
FormatLength, structure, language“Under 150 words, British English, warm, sign off as the team.”
Don’tsThe lines it must not cross“Never promise a schedule change — those go to operations.”

The official before / after table, in our clothes

The best-practices page gives four pairs — scope the task, point to sources, reference an existing pattern, describe the symptom [1]. Same four, Purple Ruler scenes.

SCOPE THE TASK“Tidy up the enrolment page.”“On the enrolment page only, make the error text under the date field readable on a phone. Change nothing else.”
POINT TO SOURCES“Why is this report wrong?”“Read docs/SPEC-… and the last three commits on this file, then tell me which rule the report breaks.”
REFERENCE A PATTERN“Add a popup.”“Add a confirm dialog the same way teacher-allocation does it — same component, same button order.”
DESCRIBE THE SYMPTOM“Fix the login.”“A school user who logs in on a tablet sees a blank page after the spinner; on a laptop it works. Fixed means the dashboard renders on both.”

And give it something it can check itself against: “Give Claude a check it can run: tests, a build, a screenshot to compare. It’s the difference between a session you watch and one you walk away from.” [1] The cost side has a rule too: “If you could describe the diff in one sentence, skip the plan.” [1]

INSIGHT D1·3

A good prompt is a draft of a rule. If you’ve pasted it three times, it wants to be a file. The third paste is the signal. That’s the moment rung 3 — tomorrow — is calling.

07 · Five cases from our desk · 10 min

Same tool, two ways of asking, and where the difference came from

All five are composites or paraphrases of real Purple Ruler sessions. No school, pupil, parent or colleague is named — and that is also the rule for your own hands-on.

CASE AOne school emailT5 prompt

A school writes: “Can we confirm the start date for the new pupil, and can the Tuesday session move to Thursday?”

✗ HOW IT WAS ASKED“Reply to this email.”

Comes back friendly and confident — and confirms the start date (we hadn’t) and agrees to Thursday (not ours to agree). Ten minutes of editing, or worse, sent as is.
✓ HOW IT SHOULD BE ASKED“You draft replies for our school-support team. Background: the start date is not yet confirmed by operations; session changes are decided by operations, not us. Here is one reply from last term with the right feel: [example]. Under 150 words, British English, warm. Never confirm a date or a schedule change — say we will come back within two working days. Draft only; do not send.”
WHERE THE DIFFERENCE CAME FROMNot the model. Two of the five elements: background (what we don’t know yet) and don’ts (what isn’t ours to promise). Role + format alone fixed the tone and still made both wrong promises — try it.
CASE B“Write it down first, then compact”T1 · T7
✗ HOW IT WAS ASKED“ctx is past 60 % — compact now and carry on.”

The summary is written by the model: it keeps what it judged important. The lane comes back with half its working state and no way to see which half.
✓ HOW IT SHOULD BE ASKEDToday, word for word from the coordinator to the Architect lane: “ctx is past 50 %: first write your progress to the status board and the hand-over file; when that is done reply with one line — ‘saved’ — and the sentinel will run /compact for you.”
WHERE THE DIFFERENCE CAME FROMOrder. /compact “keeps your requests and key code snippets, but detailed instructions … may be lost” [17]. A hand-over file is written by the lane, before the loss, and comes back from disk. The summary is lossy; the file is not. Scaled down, this is pitfall 1; tomorrow it becomes CLAUDE.md.
CASE CA parent email — draft, never sendT9 hook
✗ HOW IT WAS ASKED“Reply to the parent about the missed session and send it.”

With the mailbox tool connected and nothing in the way, it is sent — before anyone read it. Pitfall 3.
✓ HOW IT SHOULD BE ASKED“Draft a reply to the parent about the missed session. Draft only — do not send. Show me the draft and anything you were unsure about.”

And on the coordinator’s machine the sentence is redundant: the PreToolUse hook on reply / reply-all / forward / send (§03 A) stops the call before it exists.
WHERE THE DIFFERENCE CAME FROMToday, one line in the prompt. Permanently, a lock in lane 2 (Figure 14): the model can be asked to send in any wording and the tool still does not run. That is why the week ends with hooks, not with better sentences.
CASE DTwo jobs, one afternoonT3 effort · T8
✗ HOW IT WAS ASKED“Set everything to the top model and max effort, give it both jobs, go to the meeting.”

The timetable check comes back slow and over-explained; the pricing analysis comes back half-done because both were in one window (pitfall 10).
✓ HOW IT SHOULD BE ASKEDJob 1 — check next week’s timetable against the roster: low effort, you watch each result, correct on the spot. Job 2 — a pricing analysis with three options: fresh session, plan mode first, effort high, you leave for two hours and come back to a plan to approve.
WHERE THE DIFFERENCE CAME FROMEffort follows how far you step away, not how important the job feels — low is for “quick exchanges where you review each result”, high for “work where verification matters” [4]. It is “a behavioral signal, not a strict token budget” [11], and the model’s own release note says to dial it down when it over-thinks [12].
SAME ONE-LINE FIX · HIGH EFFORTAsked to change one condition. Came back with that condition changed — plus three “while I was there” edits and one line rewritten as five. Review took longer than the fix.
SAME ONE-LINE FIX · LOW EFFORTOne line changed, nothing else touched. At lower effort the model “scopes its work to what was asked rather than doing more than requested” [11].
CASE EThe third pasteT6 instruction file
✗ HOW IT WAS ASKEDFor the third time this week: “British English, under 150 words, never confirm dates, draft only…” pasted at the top of a new session.

Works — until the day you forget one line, or a colleague never had it.
✓ HOW IT SHOULD BE ASKEDPut those lines in the project’s CLAUDE.md once. Every session reads it; it comes back from disk after compact [16]; your colleague gets it for free from git. The prompt shrinks to the three facts that are new this time.
WHERE THE DIFFERENCE CAME FROMThe third paste is the signal that a prompt wants to be a file. Boris Cherny’s team: “Anytime we see Claude do something incorrectly we add it to the CLAUDE.md, so Claude knows not to do it next time.” [7] Tomorrow is this case, for an hour.

10 · Term cards

Today’s words, one line each

Same vocabulary as the Ladder page’s term map — nothing new invented here.

Context window
The session’s working memory: everything said, read and run so far. Fixed size; recall falls as it fills.
ctx %
Status-bar field showing how full the context is. Past 50 %: write progress to a file.
/compact · /clear
Compact = model-written summary, lossy. Clear = fresh window, free. Write down first; clear between unrelated tasks.
Model
Which brain answers. Status-bar field 4; /model to switch. Subagents inherit it.
Effort
A dial that follows how far you step away: low when you watch, high when you leave. Not “more is better”.
Token
The billing unit, about ¾ of a word. The whole conversation is re-sent every turn.
Prompt
What you say this time. Five elements: role, background, example, format, don’ts.
CLAUDE.md
The instruction file read every session and re-injected after compact. Only what it can’t guess. Day 2.
Permission mode
Manual · acceptEdits · plan · auto · bypass. Shift+Tab. Plan mode reads and proposes, changes nothing.
Hook
A script Claude Code runs before / after a tool call. Exit 2 blocks it. A lock, not advice. Day 3.
Skill
A folder of instructions loaded on demand. Descriptions always in context; side-effect skills should be manual.
Subagent
A helper with its own context window that returns a summary. Use it for investigation. Still on your bill.

Questions learners usually ask

  • “Should I just always use Opus?” No — most drafting is Sonnet work; Opus for judgment calls; the docs’ own diagnosis of surprise bills is “Opus left as the default” [3].
  • “Isn’t higher effort just better?” No. It follows how far you step away; on a small change it does more than you asked [11], and the release notes say to dial it down when it over-thinks [12]. And asking it in words to “think less” is unreliable — turn the dial [10].
  • “Is compact or clear better?” Neither. Clear when nothing needs to survive (free, clean). Compact early with a focus when you must keep continuity — and write down first [16].
  • “Where does what I paste go?” Into the session transcript on your machine and possibly into memory files. Treat the prompt box like an email: nothing you wouldn’t forward.
  • “Can’t I just write ‘never send’ in CLAUDE.md?” You can, and it will mostly listen — “mostly” is the point. A hook is the only thing that is not “mostly” (§03).
  • “Can it remember my prompt for next time?” Not on its own. That is literally tomorrow’s session.
