00 · Why this week · 2 min

Five days, one ladder, one hour a day

Everyone here already uses AI. The Ladder showed six rungs — chatbox → prompt → context → harness → loop → environment — and argued that the gap between a quick answer and a working system is which rung you hold the tool from. This week we climb it one rung a day, together, in Claude Code, on our own work.

01 · Rung 1 recap · 3 min

Rung 1 · The chatbox: everything evaporates

✋ SOUND FAMILIAR?
  • You explained the same thing to the AI on Monday, on Wednesday, and again on Friday?
  • A great answer last week — and you can’t find it, so you start over?

Rung 1 is where everyone starts: open a chat, type a question, get an answer, close the tab. It works. The problem is not the answers — it is that nothing survives. Every explanation, every correction, every “no, our schools call it a placement, not a booking” is gone the moment the session ends. The tool stays a stranger.

The whole of this week is about moving things out of the chat and into something that lasts: first a reusable prompt (today), then a file (tomorrow), then rules the tool cannot break (Day 3). But first, five words.

02 · Concepts · 15 min

Five words you need before you type

Almost every confusing thing a Claude Code session does — getting slow, “forgetting”, costing more than expected, answering differently today than yesterday — comes back to one of these five. Each gets one plain definition, one everyday analogy, and when you will actually meet it.

WORD 1Context/compact · /clear · /resume
Definition
The session’s working memory: everything said so far, every file it read, every command output. It has a fixed size. It fills up. When it is nearly full, Claude Code either summarises it (/compact) or you wipe it and start again (/clear).
Analogy
A whiteboard in a meeting room. Useful while there is space. When it is full you either photograph it and wipe it (compact — you keep a picture, not the board) or walk into a fresh room (clear — nothing comes with you except what you wrote down on paper).
When you meet it
The ctx % field on the status bar. A session that gets slower and starts contradicting itself. Being told “ctx is over 50% — write your progress to a file first”. The official guidance puts it bluntly: “Claude’s context window fills up fast, and performance degrades as it fills.” [1]
House rule
Before you compact, write the state down. The summary is lossy; the file is not. /clear costs nothing; /compact on a big session is itself a big request [3].
WORD 2Model/model
Definition
Which brain is answering this session. There is always more than one on offer, they differ in depth, speed and price, and the list changes over time — so the truth is never a slide, it is two places you can look right now: status-bar field 4 tells you which one you are on; /model with no argument opens the picker and lists what you can switch to [4]. For how to choose, use the docs’ own words rather than folklore: “Sonnet handles most coding tasks well and costs less than Opus. Reserve Opus for complex architectural decisions or multi-step reasoning”, and Haiku is for “fast, simple tasks” [3][4].
Analogy
A firm’s staff list. Different people cost different amounts per hour and are good at different things — and the list on the wall today is the only one that counts, not the one you remember from last year.
When you meet it
Field 4 of the status bar. Answer quality that swings for no reason. A usage window that empties faster than you expected. Switching: /model <name> switches at once; in the picker, Enter also saves it as your default [4]. On the day this page was written the docs resolve opus, sonnet and haiku to Opus 5.5, Sonnet 5.5 and Haiku 5.5 [4] — check the picker, not this sentence.
WORD 3Effort/effort · inside /model
Definition
How long it thinks before it answers. Levels run low → medium → high → xhigh → max. Higher = slower, more expensive, steadier on hard judgment; lower = quick and cheap for routine drafting. “Effort controls how much adaptive reasoning the model does.” [4] Default is high on most models, medium on the current 5.5 family.
Analogy
“Answer me now, off the top of your head” versus “take the afternoon and come back with a memo”. Same person, different depth, different cost.
When you meet it
Choosing a level in the /model picker. A reply that takes minutes when you wanted seconds. The 7-day usage window running low — effort is the first dial to turn down.
WORD 4Token & usage/usage
Definition
A token is the unit everything is counted in — roughly three-quarters of an English word. Everything you send and everything the model sends back is tokens, and the whole conversation is re-sent on every turn. Your plan gives you two rolling windows: a 5-hour one and a 7-day one.
Analogy
Mobile-plan minutes with a daily cap and a weekly cap — except a long conversation is a conference call that redials everyone each time you speak, which is why long sessions cost more per question than short ones [3].
When you meet it
/usage. Fields 6 and 7 of the status bar (5h / 7d). The message “You’ve hit your weekly limit”. The two daily glances the Ladder page recommends: ctx, and the usage windows [9].
WORD 5Prompt vs instruction file/init · /memory
Definition
A prompt is what you say this time. An instruction file — CLAUDE.md — is what is true every time; Claude Code reads it at the start of every session, automatically. “Each Claude Code session begins with a fresh context window.” [2] The file is how anything survives that.
Analogy
A request versus the staff handbook. You do not re-explain the dress code in every email; you point at the handbook.
When you meet it
The moment you paste the same paragraph for the third time (today’s INSIGHT). /init on a new folder creates a starter file; /memory opens it for editing. Tomorrow’s whole session is this file.
INSIGHT D1·1

Context fills, models differ, effort costs, tokens are the bill, and files are the only thing that lasts. Five words. If a session surprises you, one of them is the reason.

03 · Pitfalls & fixes · 8 min

Twelve ways a session goes wrong — and what to do

Each one is symptom → why → fix. Most of the “why”s are one of the five words above. The first eight are the ones to know by heart; four more are folded underneath.

The long session gets slow and strange, then starts forgetting
WHYContext is nearly full; compaction summarised away the detail you were relying on.
FIXHave it write progress to a file, then /clear and start the new session from that file. After two failed corrections on the same point, the docs say the same: clear and write a better first prompt [1].
You asked it to change one thing; it changed five
WHYThe request had no boundary, and the permission mode let edits through without asking.
FIXSay the boundary out loud: “only X, nothing else”. For anything bigger than a sentence, switch to plan mode first (Shift+Tab until the status bar says plan mode) and approve the plan before it touches anything [1][5].
You asked it to “send” the email — and it sent it
WHYThe verb was send, a sending tool was connected, and nothing stood in the way.
FIXToday: say “draft only, do not send”. Day 3: make it a rule the tool cannot break — a deny on send-type actions — because a line in a file is advice and a hook is a lock [1].
Same question, two different answers
WHYNo example and no fixed format were given, so it guessed twice; the model is not deterministic.
FIXGive one example of a good result and name the format. Facts that never change go into CLAUDE.md, not into the prompt.
You pasted something sensitive (a pupil’s name, a password)
WHYEverything in the context can end up in transcripts, memory files and logs — on your machine and in the tool’s history.
FIXNever paste it. Use placeholders (“the pupil”, “the school”). This whole week runs with a zero-names, zero-credentials rule — practise it in the hands-on.
It said “Done!” — and it wasn’t
WHYIt reported what it intended to do, and nobody checked. “Claude stops when the work looks done.” [1]
FIXAsk for evidence, not a claim: the command output, the screenshot, the read-back. The docs: “Have Claude show evidence rather than asserting success.” [1] Our house version: “no error” is not “verified”.
You complained about the format but never showed one
WHYIt can only guess what “nicer” means.
FIXOne example beats three adjectives. Paste a result you liked and say “like this”.
You used the wrong model and paid for it
WHYOpus was left as the default for a bulk, routine job — or Haiku was asked for a judgment call.
FIXMatch the model to the job, and look at status-bar field 4 before you start. Unexpectedly high spend “usually traces back to long sessions that were never cleared or to Opus left as the default model.” [3]
Four more we see every week · 09–12
You assumed it remembered yesterday
WHYSessions do not share memory unless something was written to a file.
FIX/resume to pick up the old session, or — better — write the conclusion into a file and start clean.
One message, five jobs; it did two well and lost three
WHYThe task was too big for one pass and nothing said which part mattered.
FIXOne job per ask. Or ask for the plan first and tick the parts off.
The draft came back wrong, so you blamed the AI
WHYNobody checked what it was actually given. “Claude can infer intent, but it can’t read your mind.” [1]
FIXRe-read your own ask against the five elements of rung 2 (next section): role, background, example, format, don’ts. Which one was missing?
ctx is past half and you keep going
WHYCompaction will hit in the middle of the task and take half the state with it.
FIXHouse habit: past 50%, write progress to a file before continuing. See case B below — it happened today.
04 · Rung 2 · 10 min

Rung 2 · The prompt: asking well, by hand

✋ SOUND FAMILIAR?
  • Do your best prompts live in a notes file or a sticky note you paste from — and drift a little every time?
  • When a draft comes back wrong, do you blame the AI — or check what you actually gave it?
  • Does a colleague doing the same job get different quality from the same tool? Why would that be?

Rung 2 is the discovery that how you ask changes everything. A good ask has five parts. You will not need all five every time — but when a result disappoints, one of them is missing.

ElementWhat it isOne line you might write
RoleWho it is being, for whom“You draft replies for our school-support team.”
BackgroundThe three facts that change the answer“The school is asking about a start date we have not confirmed yet.”
ExampleOne good result to copy the shape of“Here is a reply we sent last term that was about right: …”
FormatLength, structure, language“Under 150 words, British English, warm, sign off as the team.”
Don’tsThe lines it must not cross“Never promise a schedule change — those go to operations.”

The official guidance says the same thing in engineering clothes: scope the task, point to sources, reference an existing pattern, describe the symptom and what “fixed” looks like [1]. And give it something it can check itself against — a test, an example, a screenshot — because “Give Claude a check it can run … It’s the difference between a session you watch and one you walk away from.” [1]

INSIGHT 02

A good prompt is a draft of a rule. If you’ve pasted it three times, it wants to be a file. The third paste is the signal. That’s the moment rung 3 — tomorrow — is calling.

05 · Two cases from our desk · 10 min

Case A · One school email, three ways of asking

The email is a composite. No school, pupil or colleague is named — and that is also the rule for your own hands-on.

A school writes: “Can we confirm the start date for the new pupil, and can the Tuesday session move to Thursday?” Three colleagues ask the same tool for a reply.

RUNG 1 ASK
“Reply to this email.”
What comes back: a confident, friendly reply that confirms the start date (we hadn’t) and agrees to move the session to Thursday (not ours to agree). Three guesses, three chances to be wrong. Ten minutes of editing — or worse, sent as is.
RUNG 2 ASK · ROLE + FORMAT
“You draft replies for our school-support team. Warm, professional, British English, under 150 words. Reply to this email.”
What comes back: the right tone and length — but it still confirms the date and agrees to the move, because nothing told it those are not ours to promise.
RUNG 2 ASK · ALL FIVE
“You draft replies for our school-support team. Background: the start date is not yet confirmed by operations; session changes are decided by operations, not by us. Here is one reply from last term that had the right feel: [example]. Under 150 words, British English, warm. Never confirm a date or a schedule change — say we will come back within two working days. Draft only; do not send.”
What comes back: nearly sendable. Acknowledges both questions, promises a reply within two working days, commits to nothing. The difference was never the AI — it was the background and the don’ts.

Case B · “Write it down first, then compact”

This morning, one of our AI work-lanes (the Architect lane) had its context past 50% in the middle of a task. The coordinator’s instruction was, word for word: first write your progress to the status board and the hand-over file; when that is done, reply with one line — “saved” — and the sentinel will run /compact for you.

Why that order and not the other way round? Because /compact produces a summary written by the model: it keeps what it judges important and drops the rest, with no way to tell afterwards what was dropped. A hand-over file is written by the lane, before the loss, and is read back from disk by the next session. The summary is lossy; the file is not. The same habit, scaled down, is the fix for pitfalls 1 and 12 above — and tomorrow it becomes a file called CLAUDE.md.

“Anytime we see Claude do something incorrectly we add it to the CLAUDE.md, so Claude knows not to do it next time.” — Boris Cherny, who leads Claude Code at Anthropic, on his team’s shared instruction file [7]
06 · Hands-on · 5 min · in Claude Code, not the website

Write one prompt you will actually reuse

Pick the one thing you do most weeks — a reply, a summary, a status note, a checklist. Write it as a five-element prompt, run it once, and paste both the prompt and the result to the Lark group. Zero names, zero credentials.

Open a terminal, go to any folder you own, type claude. Check the status bar: which model, how full is ctx? (Fresh session: it should read near 0%.)
Paste the template below and fill the brackets. Keep the Don’ts line — it is the one most people skip.
Read the result against your ask. Which element did it ignore? Fix that one line and run it again. One correction, not five.
Paste prompt + result to the group. Save the prompt somewhere you will find it tomorrow — you will need it for homework.
## paste into Claude Code and fill the brackets
You are [role — e.g. an assistant drafting for our school-support team].
Task: [the one thing — e.g. draft a reply to the email below].
Background: [three facts that change the answer — no names].
Here is one example of a good result: [paste one].
Format: [length, structure, British English, tone].
Do not: [one to three lines — e.g. never confirm dates; draft only, do not send].
Show me the result, then list any assumption you made.
## the email / input goes here

08 · Term cards

Today’s words

Same vocabulary as the Ladder page’s term map — nothing new invented here.

Context (window)
The session’s working memory: everything said, read and run so far. Fixed size; fills up.
ctx %
Status-bar field showing how full the context is. Past 50%: write progress to a file.
/compact
Summarises the conversation so far to free space. Lossy. Write down first.
/clear
Starts a fresh conversation with empty context. Costs nothing. Use between unrelated tasks.
Model
Which brain answers. Read it off status-bar field 4; see the list and switch with /model. Pick by the docs’ rule, not by habit.
Effort
How long it thinks before answering: low → max. More = slower, costlier, steadier.
Token
The billing unit, about ¾ of a word. The whole conversation is re-sent every turn.
Usage window
Your rolling 5-hour and 7-day allowance. /usage shows both; the status bar shows them as fields 6–7.
Prompt
What you say this time. Five elements: role, background, example, format, don’ts.
CLAUDE.md
The instruction file read at the start of every session. What is true every time. Day 2.
Plan mode
A permission mode where Claude reads and proposes but changes nothing until you approve. Shift+Tab.
Status bar
The one-line dashboard at the bottom of every session: lane, repo, model, ctx, usage, mode.

Trainer notes · for the person running the hour · collapsed by default

Minute plan (60)

  • 0–2 §00 — show the week table; say the shape of every day once.
  • 2–5 §01 — two SOUND FAMILIAR questions, hands up, move on. Don’t re-teach the Ladder.
  • 5–20 §02 — five words, three minutes each. Read definition, tell the analogy in your own words, ask “when did you last meet this?”. Have a live Claude Code session on screen and point at status-bar fields 4, 5, 6–7 while you talk.
  • 20–28 §03 — don’t read all twelve. Pick 1, 3, 6, 12; ask the room which others they recognise. The page is the reference.
  • 28–38 §04 — five elements table. Ask: “which one do you always skip?” (It is Don’ts.)
  • 38–48 §05 — Case A: read the three asks aloud; let them say where ask 2 still fails before you do. Case B: tell it as a story — the point is order.
  • 48–53 §06 — everyone types. You walk the room. Nobody uses the website.
  • 53–58 three people read out prompt + result. Praise a good Don’ts line.
  • 58–60 §07 homework, one sentence. Point at D2.

Questions to ask the room

  • After Word 1: “What does your ctx say right now? Who has never looked?”
  • After Word 2: “Which of your weekly tasks is intern-grade work you’ve been sending to the partner?”
  • After Case A: “Which sentence in ask 3 stopped the wrong promise?” (The Don’ts line.)
  • After Case B: “If we compacted first and wrote the file second, what would the file be written from?”

Questions learners usually ask

  • “Should I just always use Opus?” No — most drafting is Sonnet work; Opus for judgment calls. The bill and the 7-day window are shared across your week.
  • “Is compact or clear better?” Neither is “better”. Clear when nothing needs to survive (cheapest, cleanest). Compact when you must keep continuity — and write down first.
  • “Where does what I paste go?” Into the session transcript on your machine and possibly into memory files. Treat the prompt box like an email: nothing you wouldn’t forward.
  • “It asked me for permission — what do I click?” Read what it wants to do. If it is a file edit in your own folder, fine. If it is sending, deleting or paying, say no today; Day 3 covers how to make that automatic.
  • “Can it remember my prompt for next time?” Not on its own. That is literally tomorrow’s session.
  • “What is effort, really — is it the same as model?” No. Model is who answers; effort is how long they think. Both move cost.

Things to have ready

  • A live Claude Code session with the status bar visible, ctx near 0%.
  • The Case A email in a text file so people can paste it for the hands-on.
  • The Lark group open for the paste-ins; remind everyone: zero names, zero credentials.
